    13. Conclusão

    Desenvolvemos o cliente [Flutter] da aplicação [RdvMedecins]. Para o usuário, ele oferece as mesmas telas da aplicação HTML do curso de [NestJS] e dos cursos anteriores de [Vue.js], [Angular] e [React] ; porém, esta é uma aplicação mobile instalada no celular, e o mesmo código também gera uma aplicação web.

    O servidor, por sua vez, não mudou. Sua API e JSON, cujo contrato (rotas, corpo, códigos e chaves de erro) foi suficiente para escrever o cliente sem nunca ler o seu código, atende igualmente bem a um navegador e a um celular. Há apenas uma diferença: no celular, não existe navegador para guardar o cookie do token, então a aplicação assumiu esse papel com apenas algumas linhas de código ([CookieClient]). A segurança permanece inalterada: continua sendo o servidor que autentica os usuários, verifica os papéis e as regras de gerenciamento e decide o que um paciente está autorizado a ver.

    Os leitores que fizeram o curso de [React] podem comparar:

    • ambos se baseiam na mesma ideia: a interface é uma função do estado. Um componente [React] é uma função que retorna JSX; um widget [Flutter] tem um método [build()] que retorna uma árvore de widgets. Quando o estado muda ([useState] / [setState]), a interface é reconstruída e depois comparada com a anterior;
    • O [React] gera HTML, que o navegador renderiza; o [Flutter] renderiza cada pixel por conta própria, com seu próprio engine, tanto no celular quanto no navegador. O resultado são telas idênticas em todas as plataformas, mas uma aplicação web que demora mais para carregar;
    • O [Flutter] oferece muito mais do que o [React]: os widgets do [Material], formulários, listas, janelas, animações, o tema e testes. Foram necessárias menos bibliotecas: [go_router] para os endereços, [provider] para o estado compartilhado e [http] para as requisições. Sem CSS: o layout é construído com widgets ([Column], [Row], [Padding], [Expanded]...);
    • O [Dart] é uma linguagem tipada e compilada, com tipos não anuláveis: muitos erros que o [TypeScript] deixa passar (um valor [null] ausente, um JSON lido incorretamente) são detectados em tempo de compilação ou assim que a resposta é recebida, graças ao filtro de padrões do [Dart] 3;
    • a contrapartida: telas mais verbosas (a árvore de widgets é profunda) e um ciclo de vida que é preciso conhecer ([initState], [didUpdateWidget], [dispose], [mounted]).

    Os conceitos abordados neste curso (widgets stateless e stateful, ciclo de vida, chaves, [InheritedWidget] e [provider], [ChangeNotifier], [Future] e [Stream], roteador e guards, formulários, internacionalização) são comuns a qualquer aplicação [Flutter]. Para ir além:

    • a documentação oficial, docs.flutter.dev, seus tutoriais e seu guia de arquitetura (“App architecture”);
    • testes: testes de widget ([flutter_test]), que interagem com uma tela sem um celular (as capturas de tela deste documento foram criadas com esses testes), e testes de integração ([integration_test]), que executam a aplicação real em um emulador;
    • outros gerenciadores de estado muito usados: [Riverpod] (o sucessor do [provider], do mesmo autor), [Bloc];
    • geração de código: [json_serializable] e [freezed] geram os métodos [fromJson], [copyWith], [==]... a partir de declarações simples;
    • armazenamento seguro de tokens ([flutter_secure_storage]), notificações, câmera, geolocalização: um pacote para cada necessidade, no pub.dev;
    • iPhone: o mesmo código gera uma aplicação [iOS], a ser compilada em um [Mac] com o [Xcode].
